    - So each time we get a desirable vehicle, we want to create a new pursuit scope for it. (currently done for every potential suspect)
	This scope is then replicated to the clients via UVReplicateX funcs. Both server and clients share a UVPursuitScopes table where we store scopes for all realms.
	These pursuit scopes is what we use to store states and other pursuit attributes (or maybe even some other attributes) for each vehicle separately.
	Any changes done on server are automatically mirrored to clients within UVScopeThink (or for manual updating, UVUpdateScope)
    You can pick which states/values are replicated via the table I defined: UV_SCOPE_REPLICATED_KEYS, this way you can keep server-only vars in scopes too.
    I've also added a few mini-helper functions using which I can fetch necessary data from scopes.
    Scopes are removed whenever a vehicle gets busted (we are not expecting to see this vehicle again), or the car is simply removed.

    - With this change I've also removed the use of the legacy PursuitTable approach
    This table housed all states that were once global (same states now done within scopes, as well a few other things that must remain global)
    As a replacement for PursuitTable, I have introduced a similar system that is consistent with the scope implementation: UVGlobalPursuit
    Much like scope, UVGlobalPursuit is also replicated in both realms (sharing the same table), and is updated via UVUpdateGlobalPursuit.

    SERVER

    - For handling per-scope logic, I created a function that iterates through scopes and handles all states per tick (any other per-scope Think logic should go here) - UVScopeThink
    Rest of the global states are handled inside of the base UVThink.

    - Doing this I've also taken the chance to rewrite some of the system which were, in my opinion, very hectic and a bunch of unnecessary performance hazards.
    Most, but not all systems have been rewritten in a way that they use the least amount of calls possible (traces to be specific), and should now perform better.
    Before there were many traces fired on suspects, but I've now moved all of that logic, as well as busting/evading inside of the UVThink.

    - Adding to wanted list is now done manually; before it was done for EVERY potential suspect, regardless of whether they were in the wrong or not.
    Those who are in the wanted list will be able to be chased by the police whenever they are spotted.
    Right now the only way to enter the wanted list is to cause infractions infront of another NPC Unit, or via uv_startpursuit (which adds every potential to wanted)
    Inside of NPC Validate methods, I have added a check for the enemy's scope; more specifically whether the InPursuit key for the enemy is true
    If not, it is considered an invalid entity and therefore will not be targetted (via TargetEnemy methods)
    InPursuit is set to true when UVThink considers the vehicle spotted (and they are wanted), and set to false when they actually finish their cooldown period.

    - Pursuits (UVTargeting) lasts until every scope has InPursuit set to false, or there are no scopes present.

    CLIENT

    - The clients haven't had any major changes, as a matter of fact I tried to keep it at a minimum since it would be a lot to cover.
    Due to the complexity and the length of the bullshit inside of the client code, what I instead did was fill global variables with data from scopes
    For a client who is in a pursued vehicle, I created a function which fetches an "active" scope; active scope being the scope of the vehicle the player is in.
    For clients in Unit vehicles, I check for UVHUDCopMode and if it's true, I fetch a dominant scope (scope which has the top heat or bounty), and use that data.
    Considering that Evading/Cooldown is no longer a global thing, I had to improvise with the Unit UI:
        - Evading bar fills based on the ratio of how many of the racers which are in pursuit are actually in cooldown (InCooldownCount / InPursuitCount)
        - Cooldown UI triggers whenever all racers are in cooldown
    
    I have made a few changes to the debrief, since it too used global variables; had to make it use scope variables. 
    (also had to change server debrief and make it send necessary data)
